# CTX-803: Unified S3-Compatible Webhook Ingestion (Second Brain & Homelab)

## Problem
Currently, Second Brain relies on storage-specific MinIO naming even though the actual storage may be RustFS or any S3-compatible object store. Homelab was originally designed around GitHub events. We need a unified S3-compatible webhook route and runtime naming so Cortex is not coupled to MinIO or RustFS as product names.

## Outcome
- A generic `POST /api/webhooks/s3` endpoint in the Python FastAPI layer (`src/ai_service/api.py`) accepts S3-compatible events for `second_brain` and `homelab`.
- The endpoint authenticates with `X-Cortex-S3-Token` against `CORTEX_S3_WEBHOOK_TOKEN`.
- RustFS is treated as one S3-compatible backend implementation, not a separate integration type.
- S3-compatible events are treated as dirty signals in the current implementation: any accepted event triggers full resync of the configured domain root.
- Full resync indexes current Markdown files and removes stale derived RAG rows for files no longer present.
- Integration tests simulate S3-compatible payload delivery without requiring a running object storage process.

## Proposed Setup & Architecture (Research)

### 1. The S3-Compatible Webhook Payload
The current dirty-signal payload only needs to identify the changed domain and event type. File fields are optional; when provided, Cortex validates that the absolute path stays under the configured root. Indexing still uses full root resync.

```json
{
  "source": "s3",
  "domain": "second_brain", // or "homelab"
  "event_type": "write",    // "write", "create", "remove", "rename"
  "absolute_path": "/Users/dungxbuif/workspace/second-brain/wiki/project.md",
  "relative_path": "wiki/project.md",
  "timestamp": 1718928123
}
```

### 2. The API Route (FastAPI)
In `src/ai_service/api.py`, the unified route receives events at `POST /api/webhooks/s3`. `POST /api/webhooks/rustfs` remains a compatibility alias while configs are migrated.

Required runtime settings:

- `CORTEX_S3_WEBHOOK_TOKEN`
- `CORTEX_S3_SECOND_BRAIN_ROOT`
- `CORTEX_S3_HOMELAB_ROOT`
- `SECOND_BRAIN_S3_ENDPOINT`
- `SECOND_BRAIN_S3_ACCESS_KEY`
- `SECOND_BRAIN_S3_SECRET_KEY`
- `SECOND_BRAIN_S3_REGION`
- `SECOND_BRAIN_S3_BUCKET`
- `SECOND_BRAIN_S3_PREFIX`

### 3. Full Root Resync
Decision changed during implementation: because the storage/event payload is still stabilizing, Cortex does not depend on exact per-file events. Any accepted event triggers full resync for the event domain.

- `second_brain`: scan the configured root for Markdown, reuse existing Vault document parsing/chunking/embedding, and delete stale `secondbrain_documents`/chunks no longer present.
- `homelab`: reuse `HomelabService.sync_repository(..., delete_missing=True)` with existing redaction/chunking/embedding, and delete stale `homelab_documents`/chunks no longer present.

### 4. Large Directory / Large File Scale Design
Full resync on every webhook is acceptable for current local data and early RustFS/S3-compatible development. It should not be the production path once a prefix grows large.

Target scalable behavior:

- If payload contains a trusted `bucket` + `object_key`, enqueue incremental `upsert_object` or `delete_object`.
- If payload contains rename metadata with old and new paths, enqueue `delete(old)` plus `upsert(new)`.
- If payload is missing a key or source trust is unclear, enqueue `reconcile_prefix`.
- Full prefix reconcile should be scheduled/manual, paginated, and compare S3 keys/ETags/checksums against indexed DB paths.
- Large files should be checked by object size before download: normal files index directly, medium files chunk/batch carefully, oversized files are skipped or routed to a special job.
- Embeddings should run in bounded batches with retry/backoff; webhook request handling must not perform heavy provider work inline.
