## Context

Human intent:

- Implement webhook sync for Second Brain.
- When Obsidian writes a synced object to MinIO, Cortex receives a webhook and indexes the object.
- Credentials and bucket will be supplied by the human.
- Track only the `second-brain` folder/prefix for indexing.

AI context:

- Current branch: `feat/obsidian-sync`.
- Current sprint commit: `79c501e4c67a12a1dfdf9d7af351edf7a549e6cc`.
- Existing Second Brain service already indexes one Markdown document through `SecondBrainService.index_vault_document`.
- Existing Go gateway has Second Brain capture/status/search routes but no Second Brain sync or webhook route.
- `docs/raw_spec/modules/second-brain.md` allows MinIO as backup/snapshot/mirror, but MinIO must not replace Obsidian Vault as canonical.
- `docs/raw_spec/system/source-of-truth-sync.md` requires webhooks to enqueue work, not run heavy sync inline.

Out of scope:

- Direct writes from Cortex back to the local Obsidian Vault.
- Direct PostgreSQL access from n8n or MinIO.
- Indexing objects outside the `second-brain/` prefix.
- Building the full async queue/worker platform unless required by the approved design.
- Implementing the complete audit/policy system if CTX-501/CTX-502 are not approved and available.

## Acceptance Criteria

- [x] Given a valid webhook for a changed Markdown object under `second-brain/`, when Cortex processes it, then the corresponding document is indexed through the existing Second Brain indexing pipeline.
- [x] Given a webhook for an object outside `second-brain/`, when Cortex receives it, then the object is skipped and no document/chunk is indexed.
- [x] Given a webhook without valid authentication, when Cortex receives it, then the request is rejected and no indexing occurs.
- [x] Given MinIO credentials and bucket configuration, when the sync adapter fetches an object, then secrets are not logged or persisted.
- [x] Given unchanged content with the same checksum, when the webhook is replayed, then indexing is idempotent and duplicate chunks are not created.
- [x] Failure behavior is defined for missing bucket/key, non-Markdown objects, fetch errors, malformed Markdown/frontmatter, and embedder failures.
- [x] UAT requirement: required for API behavior; verified with local/mock MinIO-compatible object fetch and webhook route tests.
